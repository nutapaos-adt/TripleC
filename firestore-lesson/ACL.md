# ACL — สิทธิ์การเข้าถึงตามบทบาท (Referral / firestore-lesson)

บทบาท (`role`) มาจาก **Firebase Auth custom claim** ที่ตั้งค่าโดย `setup-users.js` (Admin SDK) เท่านั้น —
ไม่ใช่ฟิลด์ใน Firestore ที่ผู้ใช้แก้เองได้ ทุกกฎด้านล่างบังคับใช้จริงสองชั้น: (1) UI ซ่อน/ปิดปุ่มที่ทำไม่ได้
(2) `firestore.rules` ปฏิเสธคำขอที่ฝ่าฝืนกฎ แม้ผู้ใช้จะพยายามเรียก Firestore ตรง ๆ ผ่าน console ก็ตาม

## ตารางสิทธิ์

| บทบาท | ทำได้ | ทำไม่ได้ |
|---|---|---|
| **ward_staff**<br>(เจ้าหน้าที่หอผู้ป่วย/OPD) | • เพิ่มเคสใหม่ (`referral-create.html`) — สถานะเริ่มต้น `pending_review` เสมอ<br>• ดูรายละเอียดเฉพาะเคสที่ตัวเองสร้าง (`createdBy == uid` ของตัวเอง)<br>• ลบเคสของตัวเองได้ **เฉพาะตอนสถานะยังเป็น `pending_review`** (ยังไม่มีพยาบาลตรวจ) | • ดูหรือแก้ไขเคสของเจ้าหน้าที่**คนอื่น** (query/`get` ถูก Firestore ปฏิเสธด้วย `permission-denied`)<br>• ยืนยันแผนดูแล/เปลี่ยนสถานะเคส (`plan_confirmed`/`in_progress`/`closed`) — เป็นหน้าที่พยาบาลเท่านั้น<br>• ลบเคสที่พยาบาลยืนยันแล้ว (สถานะไม่ใช่ `pending_review`)<br>• เข้าหน้าจัดการผู้ใช้ (ไม่มีในระบบนี้ — สงวนไว้สำหรับ admin) |
| **home_visit_team**<br>(พยาบาลทีมเยี่ยมบ้าน) | • ดูเคส**ทั้งหมด**ทุกเคส ทุกสถานะ (ต้องเห็นภาพรวมเพื่อรับงานต่อ)<br>• ยืนยันแผนดูแล (`pending_review → plan_confirmed`) และเปลี่ยนสถานะรอบติดตาม (`→ in_progress/closed`) — **เฉพาะเคสที่ไม่ได้สร้างเอง** | • สร้างเคสใหม่ (เป็นหน้าที่เจ้าหน้าที่หอผู้ป่วย)<br>• ลบเคสใด ๆ<br>• **ยืนยัน/เปลี่ยนสถานะเคสที่ตัวเองเป็นผู้สร้าง (ห้ามอนุมัติของตัวเอง)** — แม้ในทางปฏิบัติพยาบาลมักไม่ใช่คนสร้างเคสอยู่แล้ว แต่กฎนี้บังคับด้วย security rule เผื่อกรณีที่บทบาทซ้อนกันในอนาคต<br>• แก้ไขฟิลด์อื่นนอกเหนือสถานะ/ผลการยืนยัน (rules จำกัดคีย์ที่แก้ได้ไว้ตายตัว)<br>• เข้าหน้าจัดการผู้ใช้ |
| **admin** | • ดู/สร้าง/ลบเคสได้ทุกเคส ไม่มีข้อจำกัดเรื่อง owner<br>• ยืนยันแผนดูแล/เปลี่ยนสถานะเคสที่ผู้อื่นสร้าง เหมือนพยาบาล | • **ยืนยัน/เปลี่ยนสถานะเคสที่ตัวเองเป็นผู้สร้าง — กฎห้ามอนุมัติของตัวเองบังคับกับ admin เช่นกัน ไม่มีข้อยกเว้น** (ทดสอบแล้ว: `updateDoc` บนเคสที่ admin สร้างเองถูก Firestore ปฏิเสธด้วย `permission-denied`) |

## ทำไมถึงออกแบบแบบนี้ (อ้างอิงจากระบบต้นทาง Triple C)

- โครงสร้าง 3 บทบาทตรงกับ `App\Models\User::ROLE_*` ของระบบ Laravel ต้นทาง (ดู root `CLAUDE.md` § Roles)
- "ward_staff เห็นเฉพาะเคสของตัวเอง" คือการตีความกฎ human-in-the-loop ในบริบทของสิทธิ์การมองเห็นข้อมูล —
  เจ้าหน้าที่แต่ละคนรับผิดชอบเคสที่ตัวเองบันทึกเข้ามา ส่วนพยาบาล/แอดมินต้องเห็นภาพรวมทั้งหมดเพื่อจัดคิวติดตาม
- "ห้ามอนุมัติของตัวเอง" คือส่วนหนึ่งของกฎ **AI สร้างได้แค่ร่าง มนุษย์ต้องยืนยันเสมอ** ของระบบต้นทาง (ดู root
  `CLAUDE.md` § "The one rule…") ขยายเพิ่มอีกชั้นหนึ่ง: แม้แต่มนุษย์คนที่สร้างเคสเองก็ห้ามเป็นคนยืนยันเคสตัวเอง
  ต้องมีคนที่สองเป็นผู้ตรวจสอบเสมอ (four-eyes principle)

## บังคับใช้ที่ไหนบ้าง (โค้ดจริง)

| กฎ | UI (`js/*.js`) | Firestore Rules (`firestore.rules`) |
|---|---|---|
| ต้องล็อกอินก่อนอ่าน/เขียนทุกครั้ง | `requireLogin()` ใน `session.js` เรียกก่อนทุกหน้า | `isSignedIn()` เป็นเงื่อนไขแรกของทุก `allow` |
| ward_staff เห็นเฉพาะเคสตัวเอง | `referrals-list.js` เติม `where('createdBy','==',uid)` ในคิว | กฎ `read` ของ `/referrals/{id}` เช็ค `role() == 'ward_staff' && isOwner(resource.data)` |
| ห้ามอนุมัติของตัวเอง | `referral-detail.js` → `canConfirm()` ซ่อนปุ่มยืนยัน | กฎ `update` ของ `/referrals/{id}` เช็ค `!isOwner(resource.data)` — ไม่มีข้อยกเว้นแม้ role admin |
| แก้ได้เฉพาะช่องสถานะ | ฟอร์มไม่มีช่องแก้ไขข้อมูลเคสอื่นเลย มีแต่ปุ่มเปลี่ยนสถานะ | `request.resource.data.diff(resource.data).affectedKeys().hasOnly([...])` จำกัดคีย์ที่แก้ได้ |
| ลบต้องยืนยันก่อน | `confirm()` dialog ใน `onDelete()` | กฎ `delete` จำกัดว่าใครลบได้ (ดูตารางด้านบน) — ไม่เกี่ยวกับ dialog ฝั่ง UI |

## ทดสอบแล้ว (ดู `EVIDENCE.md`)

- ward_staff พยายามอ่านเคสของคนอื่นตรง ๆ ผ่าน `getDoc()` → `permission-denied`
- admin สร้างเคสแล้วพยายามยืนยันเคสของตัวเองทันที → `permission-denied`
- ผู้ใช้ที่ไม่ได้ล็อกอิน (`auth.currentUser === null`) พยายามอ่านเคสใด ๆ → `permission-denied`
